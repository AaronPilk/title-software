## Acceptance stories and evidence

| Story | Local result and validation |
| --- | --- |
| New company to launch | Reviewed application, milestone evidence and current authority gate launch; changes and expiry reopen it. Domain tests cover activation, unchanged save, ownership change, cross-company authority and expiry on hydration. |
| PTO to commitment | A conditional commitment allows open requirements. Current outputs bind to preparation; earlier output fails even at the same case version. Refinance does not invent a seller requirement. |
| Finals to multiple products | Each loan retains its own identity; mortgage drops DOT-specific trustee requirement. All products must be prepared before first issuance. Identical output filenames remain separate. Partial issuance locks shared inputs. |
| Missing information | Saved requests survive serialization/hydration; duplicate save is idempotent; each item resolves separately; foreign file evidence fails; resolution reopens review and does not approve the policy. |
| CPL preparation | Cash does not imply a CPL is unnecessary. Returned documents bind to the current preparation. Property or loan changes invalidate delivery eligibility. |
| Loan revision | Company/file/amount/version checked; original route cannot silently move; a single active loan's principal updates and mirrors the file; a multi-loan file requires an explicit loan choice at capture and applying touches only that loan (the other loan and the file-level amount are provably untouched) while still advancing the file's commitment version; a request whose named loan was since voided is rejected on apply and recheck rather than falling through to the surviving loan; a revised commitment uploaded before the change cannot satisfy the reply that describes it, and a later change supersedes an earlier approved reply. A field revision changes exactly one commitment field, advances the version, leaves the loan and every other field byte-identical, goes stale when the file moves, and re-baselines on recheck. |
| Company close and partner statement | Frozen rows and ownership, exact-cent reconciliation, source-change checks, immutable published allocations, older-publication rollback prevention and zero-payment loss periods are covered. |
| Period business | Receipt/rejection/recovery/closing dates remain independent when issuance month changes. Legacy unknown receipts can be backfilled once confirmed (never overwriting an existing date) and are otherwise excluded with a visible note. A rejected file's recovery stage (not yet contacted / awaiting response / lost) is derived from its outcome log, not stored, so a resumed contact after "lost" is a normal state and the badge disappears once the file recovers. |
| Repeated operations | Intake, onboarding, rejection and authority tasks deduplicate; guided sample loading is isolated/idempotent. |

### September 12, 2026 update (Claude): rejected-file recovery pipeline

- Domain suite: **74 passing tests total** (3 new for this feature — the rest grew between the entries above and now via Codex's parallel company-materials work, merged into `main` separately: see `docs/company-materials-publication.md`). The 3 new tests cover the full contacted/awaiting-response/lost/resumed/recovered cycle on a derived `recoveryStage`; contacted/recovery-lost checkpoints rejecting on a non-rejected order; and receipt-date backfill filling once, then rejecting both a second attempt and a future date. TypeScript checking: passed. Production build: passed.
- Added `recoveryStage()` in `lib/title/business.ts`: derived, not stored — scans a rejected order's existing `outcomes[]` log backwards and reports "Not yet contacted" / "Awaiting response" / "Lost" from whichever of Rejected/Contacted/Recovery lost happened most recently, and `null` once the order is no longer Rejected. This follows the codebase's existing fingerprint style of computing truth from an event log rather than adding a second mutable field that could drift from it. A later "Contacted" is allowed after "Recovery lost" — a contact that seemed lost can genuinely resume — so the cycle can repeat before an eventual "Recovered".
- Added `backfillReceivedDate()`, deliberately backfill-only: it fills a legacy order's missing `receivedAt` but throws if one is already present, and rejects a future date. An existing date is intentionally left alone rather than made "correctable" here, since letting a period-based report move after the fact is a materially different, more sensitive change than filling in one that was simply never recorded.
- UI (`components/title/policies.tsx`): the order detail sheet shows a second status pill for the recovery stage next to the order-status pill; a "Backfill receipt date" control appears only while `receivedAt` is missing and disappears once saved; the outcome recorder offers suggested (fully editable) wording chips for Contacted/Recovery lost, explicitly documented in-code as starting points, not an approved fixed taxonomy.
- **A real, pre-existing bug was found only by driving the running app, exactly the kind of defect this verification step exists to catch**: `OrderOutcome` and `OrderNotes` — two unrelated sibling components, both present since the original MVP commit — were given the literal same React `key` (the order id), which is invalid whenever siblings share a key. It was latent because nothing previously changed the shape of the sheet's children array while a file stayed open; the new backfill control's conditional disappearing after save was the first thing to do that mid-session, which surfaced a `console.error` ("Encountered two children with the same key") and, worse, made React actually duplicate the outcome section in the live DOM (confirmed via a DOM dump: two `.form-stack` sections, two "Order outcome" comboboxes, at different vertical offsets in the same sheet). Fixed by giving each component a distinct `${id}:outcome` / `${id}:notes` key, so both still reset their local state on order switch without colliding. Playwright's `:visible` pseudo-selector was tried first (on the theory that this was an animation artifact) and did not resolve it, which is what pointed at a real render bug rather than test flakiness.
- Verification performed: picked a non-Issued/non-Rejected order missing a receipt date from the default seed; backfilled its receipt date through the real UI and confirmed the grid cell updated and the control disappeared; then drove the full reject → contact (via a template chip) → recovery-lost (via a template chip) → resumed-contact → recovered cycle through the real UI, confirming the correct status-pill pair at every stage (`["Rejected","Not yet contacted"]` → `["Rejected","Awaiting response"]` → `["Rejected","Lost"]` → `["Rejected","Awaiting response"]` → `["Needs review"]` with no recovery badge after recovery), the exact template-chip text landing in the note field, and a complete, correctly-ordered outcome log. Zero console errors after the key-collision fix.
