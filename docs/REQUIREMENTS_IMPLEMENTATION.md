# Ballantyne requirements: implementation and production readiness

Updated September 23, 2026. This records the implementation against the supplied **AI System Developer Requirements — Revised** (26 pages) and **Information Needed Before Production** (10 pages). The original PDFs remain outside the repository. Their proposed operating rules still require business confirmation where the documents differ.

**Current release status:** Agency/Production views, company onboarding, staff invitation/assignment controls, original-document handling, OCR, multiple-company Missive routing and workspace credential settings are implemented in the private pilot. The September 22 security release fixes six confirmed application defects, updates dependencies and adds regression coverage; see [the security evidence](testing/security-remediation-2026-09-22.md). The subsequent workflow pass fixes source-capture, OCR-review and financial-review defects and adds a [current product comparison](research/product-comparison-2026-09-22.md). The September 23 follow-up adds reviewed document-to-field suggestions, source/correction evidence and independent original-byte archives, with a zero-warning lint gate; see [pilot readiness evidence](testing/pilot-readiness-2026-09-23.md). Owner connection setup and a signed-in staff acceptance walkthrough remain pending. Older verification sections below are historical, not current deployment claims.

**SoftPro Select remains the intended production authority. Its integration is deferred until last at the owner's September 23 request, pending direct vendor access.** The application now has a working preparation and review layer around that model. It has no live SoftPro reader, writer, order-creation API, database integration or screen automation. A saved mapping or human-recorded outcome does not establish a vendor connection.

## What is implemented

| Requirements | Current implementation | Remaining dependency or limit |
| --- | --- | --- |
| Agency management and Production workspaces | Agency and Production navigation have separate starting pages and relevant queues. Authorized agency staff can switch to Production; company creation supports one company or a JV portfolio. | Views do not grant permissions. Real company records, staff scopes and daily staff acceptance still need owner confirmation. |
| JV ownership, company documents and member reporting | Versioned ownership history, company-material review/publication, period-specific closes/member statements and delivery records are implemented. | Financials are operational reporting, not a trust-accounting ledger, three-way reconciliation, banking connection or money-transfer system. |
| Staff setup and assignments | Owner-reviewed invitation records, lifecycle/revocation controls, verified account assignments, personal password setup and MFA requirements are implemented. | Preparing access does not send mail. Setup email needs approved sender configuration/server flags and an explicit send; staff must complete their own sign-in. See [staff access](staff-access.md). |
| One Select environment with separate JV companies; configurable company context | **Connections → Setup** records versioned company identifiers/names, underwriter, inbox aliases, template, archive rule, existing SoftPro 360 channel and named approvers. Current profiles must share one environment; external company identifiers and inbox aliases cannot collide. | Staff must supply and verify the actual Select identifiers, company rules and permitted vendor actions. These records are human attestations. |
| Exact technical field mappings | Each company can record actual external field identifiers, read/write direction, risk and verification evidence. Unsupported fields and duplicate mappings are rejected. | Current logical fields are address, buyer/insured, seller, lender, loan amount, legal description, county, attorney and attorney email. Sales price, policy/coverage fields, endorsements, statuses, tasks and other vendor actions need additional mappings and supported connector implementation. |
| Company-scoped file matching and conversation continuity | Versioned links retain the company/environment, external file ID/number and optional Missive conversation ID. Candidate search prioritizes exact file/thread references, normalizes common address abbreviations and exposes conflicts. Name-only or ambiguous results never select a file automatically. | Search covers recorded local links, not the live Select inventory. Duplicate prevention before creating a real SoftPro order remains a connector acceptance test. |
| Repeated revisions with source and old/new values | **Connections → Review queue** captures the manually observed SoftPro value, requested value, source document/version/page/quotation, observation evidence and reason. Named approval and a review note are required before recording an applied outcome. Histories and audit events are immutable. | The before-value is manually read and attested, not fetched from SoftPro. Outcomes distinguish human-recorded results from actual API execution. Nothing here writes local values back into SoftPro. |
| Stale-data protection and final-policy exceptions | Proposals become stale after relevant local order/policy, document, mapping, profile, link or control changes. Postclosing/final-preparation changes and untargeted multi-loan amount changes enter an exception state. Unresolved same-file external proposals block final readiness, policy preparation/issuance and outstanding prepared-policy handoffs; rejected or recorded requests release that proposal gate. Issued history stays intact. | A connector must re-read authoritative SoftPro values immediately before any future write and reconcile downstream calculations/documents. The business must approve its exact final-readiness checklist and correction procedures. |
| Observe/propose modes and immediate stop | Company controls default to **Observe**. **Propose** permits reviewed preparation. Pausing blocks new proposals, approvals and recording applied outcomes; history remains readable. A stale/paused approved proposal can still be recorded as **Not applied**. | There is no automatic-write mode. Both PDFs' medium/high-risk approval expectations are met conservatively by requiring named human approval in this workflow. Production approval ownership still needs sign-off. |
| Missive messages, attachments and event intake | Existing reviewed message import preserves conversation/message identity and original source history. New server code saves selected original attachment bytes with immutable attribution and SHA-256 metadata. A signed webhook receiver durably queues source metadata for review. Mapping is rechecked atomically at enqueue, message import and queue completion commit together, and pending pages retain former routing after a mapping change. Receiving or reading an email never completes a title file. | Version 2 routing supports one company or a portfolio of approximately 25 JVs, with up to 500 routes. One inbox can have several approved company destinations; shared events require a reviewed company/file choice. Automatic classification, provider-side notes/labels/drafts, outbound sending and scheduled polling are not implemented. The routing migration and API/UI are deployed. Actual inbox/company approvals and a live message-import acceptance case remain to be completed. |
| Document extraction with inspectable sources | **Documents → Read document text** reads selectable PDF text or a selected scanned page/image. Final-source **Capture fields → Find field suggestions** proposes existing deed/security fields with exact quote/page evidence, ambiguity warnings and retained corrections. Original review is required before saving assisted capture; saved fields remain unapproved. See [review instructions](document-field-review.md). | Browser-local printed-English OCR; 25 MB, 120 PDF pages, 12 MP source images, 4 MP rendered pages. Field suggestion runs read up to six scanned pages and explicitly list unread pages. Assets are same-origin; no OCR document upload. Handwriting, faint scans, legal interpretation and critical wording need manual review. Staff originals are still needed to measure accuracy. No SoftPro write or automatic model training. |
| Workspace-specific Missive credentials | **Settings → Missive account connection** verifies a complete token before saving it encrypted in Supabase Vault for that workspace. Replacement/disconnection pauses routes and invalidates old reviews. Status responses omit the secret; workspace state, backups and audit details do not contain it. | The migration and API/UI are deployed. The verified token has not yet been saved in the hosted workspace; owner sign-in and credential setup remain pending. The complete supplied token has passed read-only Missive directory discovery; a fresh token is not currently required to resolve the earlier prefix error. |
| Shared work, permissions, audit and recovery | Existing Supabase-backed commands, company permissions, restricted-document access, conflict checks, private files and metadata recovery points also cover the new records. Company integration history is withheld together when restricted evidence would otherwise expose an incomplete history. | Independent originals archives and verified file recovery downloads are now implemented. A real hosted byte-recovery drill, business retention, operational ownership and signed-in acceptance remain required before bulk import. This does not change SoftPro permissions or audit retention. |
| Production-readiness checklist | Connections records evidence for vendor method, company/field mappings, samples, approvals, templates/360 channels, storage, support and acceptance. Changes retain their history. | A **Ready** checkbox is a business attestation, not API verification or production certification. |

The existing per-user staff assistant persists separate conversations and can request parallel specialist reviews of permitted app records. It can propose reviewed staff tasks. It does not operate SoftPro, automatically classify incoming mail or automatically turn PDF/OCR text into business-field updates. ## What Ballantyne needs to provide next

1. **Confirm which real company each connection belongs to.** This is the meaning of “company mappings”: the application company/JV, its company profile inside Select, the inboxes it uses, its underwriter/templates and the people allowed to work there. Start with the existing legal-company list. A shared inbox can belong to several JVs and requires a destination choice; a single-company business needs one company. We can build the routing, but cannot infer the correct legal entity or vendor identifier from a display name. Record verified values in Connections and leave unknown identifiers missing.
2. **Leave SoftPro integration until last, as requested September 23.** When ready, contact the representative for the account's supported integration, entitlements, contract, authentication, test environment and field/action documentation. Existing underwriter channels remain external. Company/document review and pilot feedback can proceed without a live SoftPro connector.
3. **Approve the business rules.** Name medium/high-risk and final-policy approvers; define readiness, downstream regeneration, late-change, ambiguous-match, cancellation and escalation rules. Decide permitted Missive communications, retention, support, account ownership and recovery responsibilities. Automatic-write permissions remain disabled.
4. **Provide representative acceptance cases.** Use owner-authorized originals in the private workspace, or fictional fixtures for public/automated tests, spanning new orders, repeated revisions, same-name borrowers, multiple loans, unrelated transactions in one thread, conflicting companies, missing/scanned documents, recording completion and late policy changes. Blanket redaction is not required for private workflow validation. Keep originals out of public GitHub and compare results with staff's actual SoftPro work, including time/error measurements.
5. **Finish the Missive connection and approved routing.** The complete token now passes discovery. The owner or organization-wide administrator can now use **Settings → Missive account connection** to verify and save the complete token in encrypted workspace storage. Review each company/inbox route, including shared inboxes. Event intake still needs server-side workspace/rule/signing configuration; attachment downloads need the exact approved HTTPS origins. Follow the [Missive setup guide](missive-connection.md). Do not place tokens in source files or browser build variables.
6. **Accept the deployed pilot.** Sign in through Cloudflare and the app, assign the intended company permissions, verify real access and attachment origins, then demonstrate one complete representative case with staff. Start with Observe/Propose. Record business acceptance before introducing any future vendor write capability.

OneDrive upload automation, production monitoring/alerts, automated-processing accuracy and time-saved reporting, vendor-side retries/reconciliation and actual SoftPro integration acceptance remain work to complete after the corresponding business rules and supported access are available.
