# Ballantyne requirements: implementation and production readiness

Updated September 14, 2026. This records the implementation against the supplied **AI System Developer Requirements — Revised** (26 pages) and **Information Needed Before Production** (10 pages). The original PDFs remain outside the repository. Their proposed operating rules still require business confirmation where the documents differ.

**SoftPro Select remains the intended production authority.** The application now has a working preparation and review layer around that model. It has no live SoftPro reader, writer, order-creation API, database integration or screen automation. A saved mapping or human-recorded outcome does not establish a vendor connection.

## What is implemented

| Requirements | Current implementation | Remaining dependency or limit |
| --- | --- | --- |
| One Select environment with separate JV companies; configurable company context | **Connections → Setup** records versioned company identifiers/names, underwriter, inbox aliases, template, archive rule, existing SoftPro 360 channel and named approvers. Current profiles must share one environment; external company identifiers and inbox aliases cannot collide. | Staff must supply and verify the actual Select identifiers, company rules and permitted vendor actions. These records are human attestations. |
| Exact technical field mappings | Each company can record actual external field identifiers, read/write direction, risk and verification evidence. Unsupported fields and duplicate mappings are rejected. | Current logical fields are address, buyer/insured, seller, lender, loan amount, legal description, county, attorney and attorney email. Sales price, policy/coverage fields, endorsements, statuses, tasks and other vendor actions need additional mappings and supported connector implementation. |
| Company-scoped file matching and conversation continuity | Versioned links retain the company/environment, external file ID/number and optional Missive conversation ID. Candidate search prioritizes exact file/thread references, normalizes common address abbreviations and exposes conflicts. Name-only or ambiguous results never select a file automatically. | Search covers recorded local links, not the live Select inventory. Duplicate prevention before creating a real SoftPro order remains a connector acceptance test. |
| Repeated revisions with source and old/new values | **Connections → Review queue** captures the manually observed SoftPro value, requested value, source document/version/page/quotation, observation evidence and reason. Named approval and a review note are required before recording an applied outcome. Histories and audit events are immutable. | The before-value is manually read and attested, not fetched from SoftPro. Outcomes distinguish human-recorded results from actual API execution. Nothing here writes local values back into SoftPro. |
| Stale-data protection and final-policy exceptions | Proposals become stale after relevant local order/policy, document, mapping, profile, link or control changes. Postclosing/final-preparation changes and untargeted multi-loan amount changes enter an exception state. Unresolved same-file external proposals block final readiness, policy preparation/issuance and outstanding prepared-policy handoffs; rejected or recorded requests release that proposal gate. Issued history stays intact. | A connector must re-read authoritative SoftPro values immediately before any future write and reconcile downstream calculations/documents. The business must approve its exact final-readiness checklist and correction procedures. |
| Observe/propose modes and immediate stop | Company controls default to **Observe**. **Propose** permits reviewed preparation. Pausing blocks new proposals, approvals and recording applied outcomes; history remains readable. A stale/paused approved proposal can still be recorded as **Not applied**. | There is no automatic-write mode. Both PDFs' medium/high-risk approval expectations are met conservatively by requiring named human approval in this workflow. Production approval ownership still needs sign-off. |
| Missive messages, attachments and event intake | Existing reviewed message import preserves conversation/message identity and original source history. New server code saves selected original attachment bytes with immutable attribution and SHA-256 metadata. A signed webhook receiver durably queues source metadata for review. Mapping is rechecked atomically at enqueue, message import and queue completion commit together, and pending pages retain former routing after a mapping change. Receiving or reading an email never completes a title file. | The current importer supports one approved team-inbox → company mapping per workspace. Multi-inbox production routing, automatic classification, provider-side notes/labels/drafts and outbound sending are not implemented. Valid credentials and server configuration are required. |
| Document extraction with inspectable sources | **Documents → Read document text** reads selectable PDF text in the browser, page by page, and copies excerpts with document/version/page references. Original files remain unchanged. Limits are 25 MB, 120 pages and bounded processing time/text size. | This is text extraction, not OCR or automatic structured-field interpretation. Scanned, encrypted, unreadable or partially textless documents visibly require review. Extracted text is not automatically saved into title fields or sent to a model. |
| Shared work, permissions, audit and recovery | Existing Supabase-backed commands, company permissions, restricted-document access, conflict checks, private files and recovery points also cover the new records. Company integration history is withheld together when restricted evidence would otherwise expose an incomplete history. | Business retention, independent disaster recovery, operational support ownership and production acceptance remain to be agreed. This does not change SoftPro permissions or audit retention. |
| Production-readiness checklist | Connections records evidence for vendor method, company/field mappings, samples, approvals, templates/360 channels, storage, support and acceptance. Changes retain their history. | A **Ready** checkbox is a business attestation, not API verification or production certification. |

The existing per-user staff assistant persists separate conversations and can request parallel specialist reviews of permitted app records. It can propose reviewed staff tasks. It does not operate SoftPro, automatically classify incoming mail or interpret these newly readable PDFs. See [Personal staff assistant](personal-assistant.md) for the actual model/data boundary.

## Deployment and verification

The new Connections workflow, attachment importer, PDF reader and webhook changes are deployed to the existing [private Cloudflare pilot](https://title-software-pilot.aaron-9c3.workers.dev/) on September 14. Application commit `fd8c824` is on local `main`; nothing was pushed to GitHub during this pass. The frontend Worker version is `4b6d158d-1784-43a0-8353-fdc39cca1de8`, `title-api` is version 9 with JWT verification, and the dedicated HMAC receiver `title-missive-events` is version 1. Both new migrations are applied, bringing the database history to twelve migrations. Local migration filenames match the server-assigned versions.

Cloudflare still protects the hostname and Worker for the seven approved staff emails; preview URLs remain disabled. Live checks returned the Access sign-in redirect, HTTP401 for an unauthenticated API request, and HTTP503 with **Event intake is not configured** from the new receiver. Database RPC permissions remain server-only. The project still has one workspace, seven users/memberships and no uploaded assets or queued jobs. No real mail or title records were imported. Supabase's security advisor reported only the existing informational RLS-without-policy entries for server-only tables; [advisor explanation](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

The in-app browser reached Cloudflare's sign-in screen. A fresh authenticated hosted walkthrough remains pending; the tested synthetic browser workflows below do not substitute for that acceptance step.

Final verification passed **454 tests per round × five rounds = 2,270 passing cases**: 220 domain, 112 backend, 58 Missive, 13 PDF, 34 workflow and 17 assistant tests per round. Web and assistant TypeScript checks, targeted component lint, both Edge bundles and the local production build passed. The existing large client-chunk warning remains.

The disposable local PostgreSQL runner passed **224 transaction assertions across five rounds**, including mapping conflicts, attachment receipts, event deduplication, pending pagination and a simulated queue failure that rolls back the whole import. Run `npm run test:missive:sql` from `web/` with PostgreSQL tools installed; it creates a socket-only temporary database and removes it afterward.

Browser verification exercised Connections setup → proposal → approval → manual receipt, revised confirmations, reload persistence, ambiguous matching, mobile layout, Missive event pagination/routing/import/attachment controls, and production PDF worker/page/clipboard behavior. Browser fixtures used synthetic records; Missive/Auth/API transport was intercepted where applicable. PDF review made no outbound provider requests and left original bytes and saved workspace state unchanged. These checks do not establish real Missive or SoftPro connectivity, OCR, vendor policy issuance or business acceptance.

## What Ballantyne needs to provide next

1. **Confirm the operating matrix.** Supply every actual Select company identifier/name, inbox/alias, underwriter/360 channel, template, numbering convention, archive destination and user scope. Record these in Connections; keep unknowns marked missing.
2. **Obtain supported SoftPro integration access.** Ask SoftPro for Ballantyne's licensed ProInterface/API/SDK documentation, approved authentication method, service-account permissions, test environment and supported field/action identifiers. Continue using existing AgentNet, agentTRAX and WFG channels through SoftPro 360. No new separate underwriter connector is assumed.
3. **Approve the business rules.** Name medium/high-risk and final-policy approvers; define readiness, downstream regeneration, late-change, ambiguous-match, cancellation and escalation rules. Decide permitted Missive communications, retention, support, account ownership and recovery responsibilities. Automatic-write permissions remain disabled.
4. **Provide representative acceptance cases.** Use approved anonymized examples spanning new orders, repeated revisions, same-name borrowers, multiple loans, unrelated transactions in one thread, conflicting companies, missing/scanned documents, recording completion and late policy changes. Compare results with staff's actual SoftPro work and capture baseline time/error measurements.
5. **Configure and validate Missive on the server.** Store a working `MISSIVE_API_TOKEN`, the intended `MISSIVE_WORKSPACE_ID`, a `MISSIVE_WEBHOOK_SECRET` of at least 32 characters, and exact approved HTTPS attachment origins in `MISSIVE_ATTACHMENT_ORIGINS`. Use the receiver URL `https://<project-ref>.supabase.co/functions/v1/title-missive-events`. For initial rule validation, set `MISSIVE_WEBHOOK_VALIDATION_ONLY=true`: correctly signed validation requests are accepted but nothing is queued. Create the rule, record its ID in `MISSIVE_WEBHOOK_RULE_IDS`, then disable validation-only mode. Verify the reviewed inbox/company mapping before enabling intake. Secrets belong in the server secret manager, not this document or browser configuration.
6. **Accept the deployed pilot.** Sign in through Cloudflare and the app, assign the intended company permissions, verify real access and attachment origins, then demonstrate one complete representative case with staff. Start with Observe/Propose. Record business acceptance before introducing any future vendor write capability.

OneDrive upload automation, production monitoring/alerts, automated-processing accuracy and time-saved reporting, vendor-side retries/reconciliation and actual SoftPro integration acceptance remain work to complete after the corresponding business rules and supported access are available.
